# 手机出口对照：扫码配对交互设计

状态：设计稿，未实现。维护者 2026-11-25 选定“扫码配对”方案。README 里“没有 telemetry、没有第三方依赖”的声明对当前版本仍然成立；本文写到的外部请求要等实现时才会有（见第 6 节）。

## 1. 目的和边界

用户常常同时用 Mac 和手机，两台设备的网络出口可能不在同一个国家或地区，用户自己往往不知道。这个功能只做一件事：**让用户知道两台设备的出口位置可能不同，同时看到“这台 Mac 现在从哪里出去”和“手机现在从哪里出去”。**

对照结果不是订阅或付款的前置条件。“相同”不代表合规或可以付款，“不同”也不意味着应该去改网络。

边界（与 [AGENTS.md](../AGENTS.md) 的范围条款一致）：

- 只提醒，不拦截，不改任何网络设置，不替用户切换出口。
- 不判断出口“对不对”、能不能让账号或付款通过。出口位置不等于服务资格，平台按真实所在地和账号信息判断（[roundtable.md](roundtable.md) 共同证据包里的 A1、O2）。
- 不对不一致的情况给出任何绕开地区限制或平台风控的建议。
- 只显示到国家或地区一级，不显示城市、运营商或 IP。

## 2. 什么时候出现

| 时机 | 行为 | 说明 |
|---|---|---|
| 用户主动 | 菜单新增一项“对照手机出口…”，随时可用 | 主入口，永远可用 |
| 查看出口检查结果时 | “检查 Claude 出口 / 检查 Codex 出口”的结果弹窗（现在是 `NSAlert`，可以用 `addButton` 加第二个按钮）里，加一个“对照手机出口”按钮。按钮名不出现“付款前”字样，免得用户把对照结果当成付款的一环 | 那个检查调用的是已安装的 `claude-safe` / `codex-safe` 预检适配器，不是 Hachi 自己的出口地区查询，所以这个按钮只是一个快捷入口，打开的仍是第 3 节的窗口；Mac 侧出口查询（第 6 节）做好之前，这个按钮不出现。Hachi 是菜单栏应用，看不到浏览器里打开了什么页面，所以不做“自动识别付款页”。用户在订阅或付款这类时候常会先看一下出口检查结果，这个入口放在那里方便顺手对照，但界面上不提付款 |
| 网络变化 | 网络变化稳定 30 秒后，菜单栏图标旁出现一个小圆点，菜单顶部出现“网络变了，要对照手机出口吗？” | 不弹窗、不发系统通知、不自动出二维码。触发条件见下面的说明 |

“网络变化”怎么算：`NWPath` 不提供网络标识（同名 Wi‑Fi 之间切换也分不出来），所以不按“是不是同一个网络”判断，只看正在使用的物理接口类型（Wi‑Fi、有线、蜂窝）有没有变化。**不检测 VPN、代理或隧道接口**：Hachi 不去判断用户有没有在用这些工具，也不记录、不展示。提示的意思只是“你换了网络，出口可能也变了”，文案不出现“对齐”“保持一致”之类的说法。规则：

- Hachi 只在内存里记一个值：上一次路径可用时，正在使用的物理接口类型（Wi‑Fi、有线、蜂窝之一）。`NWPath` 报告的 `.other`（隧道、虚拟网卡等）和 `.loopback` 一律忽略，不参与判断，也不触发提示。
- 路径可用时，如果当前物理接口类型和记住的值不同，算一次变化，并更新这个值。路径不可用时不更新；之后恢复可用、接口类型和记住的一样（例如睡眠唤醒、短暂掉线），不算变化。
- “当前物理接口类型”的取值：`NWPath` 没有“唯一在用的接口”，`usesInterfaceType(_:)` 可能对多个类型同时为真。按固定优先级取第一个为真的：有线 > Wi‑Fi > 蜂窝。例如有线和 Wi‑Fi 同时在用时记“有线”，拔掉网线后变成“Wi‑Fi”，算一次变化。
- 实现 PR 要把这段判断写成不依赖 `NWPathMonitor` 的纯函数，用注入的路径状态序列测试（包括睡眠唤醒、Wi‑Fi 切有线、有线和 Wi‑Fi 并存、出现 `.other` 接口这几种）。
- 变化后要稳定 30 秒才提示，期间再变就重新计时。
- 不管怎么变，两次提示至少隔 10 分钟。
- 提示的样子：菜单顶部多两项，第一项是“网络变了，要对照手机出口吗？”，点它打开第 3 节的窗口；第二项是“这次不用”，点它只清除提示。
- 小圆点和这两项在以下任一情况下消失：用户点了其中一项；用户从任何入口打开了对照窗口；30 分钟内没有操作。点“这次不用”后，下一次网络变化前不再提示。

盲区：在同一个网络下开关或切换 VPN、代理时，这条规则不会提示。所以“网络变化提示”不能代表出口变了，出口变化只能靠用户主动对照。

这个时机的价值要在实现后看实际打扰程度再定，如果误报多或者用户觉得打扰，可以先去掉这个提示（预检弹窗里的入口另见第 7 节第 5 条）。

二维码只在用户点了上面某个入口之后才生成和显示。Hachi 不在后台定时让手机去查。

## 3. 主流程

1. 用户点“对照手机出口…”。
2. Mac 先查自己的出口地区（见第 6 节依赖），然后弹出窗口：左边是二维码，右边是“这台 Mac：<地区>”。
3. 用户用手机相机扫码，手机浏览器打开检查页。
4. 检查页只显示一行大字“这部手机：<地区>”，下面一行小字是隐私说明（文案见第 4 节，承诺见第 6 节），再下面是“回到 Mac 上对照”。
5. 用户回到 Mac 窗口。窗口在各状态下的按钮见下表。
6. 选“两边显示相同”：窗口里显示一行“你确认两边显示的地区相同。这只是你此刻看到的结果，不代表应用商店或平台看到的是同一个地区。”，用户点“关闭”后窗口关闭。**菜单里不留任何对照记录**，免得过一阵子再看到“相同”被当成可以付款的信号（见第 7 节第 4 条）。
7. 选“两边显示不同”：进入第 4 节的提醒。因为手机不回传结果，扫码路径下 Mac 不知道手机具体是哪个地区，提醒里只写 Mac 这一侧的地区，不替用户填手机的地区。

窗口按钮，按状态：

| 状态 | 可用的按钮 |
|---|---|
| Mac 侧查到了地区，显示二维码 | 两边显示相同 / 两边显示不同 / 扫不了 / 关闭 |
| “扫不了”第一步（显示短地址） | 两边显示相同 / 两边显示不同 / 手动填写 / 关闭 |
| “扫不了”第二步（手动填写） | 下拉列表 + 确定 / 我不知道 / 返回 |
| Mac 侧查不到地区 | 重试 / 关闭（二维码和短地址照常显示，用户可以自己看手机的结果，但不能比较，也不留记录） |

第一版里手机**不把结果传回 Mac**，由用户自己看两边的地区并点按钮。这样二维码里不需要任何会话标识，Mac 和检查页之间也没有连接。以后如果要自动对照，另开 issue 讨论（第 7 节）。

二维码内容只是固定的检查页地址，不带设备、用户或会话参数。因为地址固定，旧截图扫出来也是同一个页面，而页面只显示访问者自己当前的出口，所以旧码无害，不设过期机制。

## 4. 文案

本节文案是**实现前草稿**，不是定稿。其中所有隐私承诺（“我们不保存 IP”“不用 Cookie”等）都未经验证，在第 6 节的发布前置条件满足之前，不得进入任何构建。其中“我们不保存 IP”只对 Hachi 自己运营的检查页成立：如果 Mac 侧或检查页用了第三方地区查询服务，第三方会看到 IP，这句话对它不成立，文案必须改成如实说明（例如“地区查询由 <服务名> 提供，它的隐私政策见 <链接>”），不能写“我们”。

### Mac 窗口

- 标题：对照手机出口
- 说明：用手机相机扫这个码，手机会打开一个页面，显示手机现在的网络出口在哪个国家或地区。看完回来点下面的按钮。
- Mac 侧：这台 Mac：日本（JP）
- Mac 侧查询失败：这台 Mac：暂时查不到。按钮见第 3 节表格最后一行，不在菜单里留任何对照记录。
- 按钮：见第 3 节表格
- 二维码下方小字：扫不了的话，在手机浏览器里输入 <检查页短地址>
- 底部小字：只看国家或地区。我们不保存 IP，也不把手机的结果传回这台 Mac。

### 手机检查页

- 主文字：这部手机：日本（JP）
- 查询失败：暂时查不到这部手机的出口，请稍后刷新重试。
- 隐私说明：这个页面只读取你的网络出口所在的国家或地区。我们不保存 IP，不用 Cookie，不收集其他信息。只有你打开这个页面时才会查询。
- 底部：回到 Mac 上对照

### 两边不同时的提醒（Mac）

- 标题：你看到两台设备的网络出口不在同一个地区
- 正文：
  > 这台 Mac：日本（JP）
  > 这部手机：和上面不同（以手机页面显示为准）
  >
  > 这只是提醒。Hachi 不判断哪一个“对”，也不会帮你修改网络。
  >
  > 拿不准的话，请直接联系应用商店或对应服务的客服确认。
- 按钮：知道了

提醒里不出现“切换节点”“换成某地出口”“关掉/打开 VPN 再付款”之类的建议，也不出现“这样更安全”“不会被封”之类的承诺。

## 5. 手动兜底

扫不了码（没有相机权限、相机打不开链接）时，用户点“扫不了”：

- 第一步：显示检查页的短地址，说明“在手机浏览器里输入这个地址，结果和扫码一样”。看完后用上表第二行的按钮。这一步仍然只用 Hachi 自己的检查页，不引导用户去第三方 IP 查询网站。
- 第二步（点“手动填写”；手机不在身边，或检查页打不开时用）：说明“如果你已经知道手机现在的网络出口在哪个国家或地区，可以在这里选。这是你自己填的，Hachi 没法核实。”控件是国家或地区下拉列表（ISO 3166 列表，默认空），以及“我不知道”。
  - 这里只接受网络出口地区。应用商店账号的地区是另一回事（出口在美国的手机，商店账号可以设成日本），不能拿来代替，说明里写明“不要填应用商店账号的地区”。
  - 选了地区：和 Mac 侧比较。相同时窗口里显示“你填的手机地区和这台 Mac 相同（未核实）”，关闭后同样不在菜单里留记录；不同时显示第 4 节的提醒，标题改为“你填的手机地区和这台 Mac 的出口不在同一个地区”，手机一行写“你填的：<地区>（未核实）”。
  - 选“我不知道”：只显示一句“没关系。有疑问的话，请联系应用商店或对应服务的客服。”，然后关闭。

Mac 侧出口查不到时，手动填写不可用，因为没有可比较的对象（见第 3 节表格最后一行）。

手动填的地区同样只存在内存里，不写磁盘。

## 6. 隐私说明和实现约束

对用户的承诺（同时写在手机检查页上）：

- 检查页只读取出口所在的国家或地区。
- 不保存 IP，不用 Cookie、本地存储或第三方统计脚本，不收集设备型号、浏览器指纹或位置权限。
- 只有用户打开页面（扫码或输入短地址）时才查询，Hachi 不会在后台让手机发请求。

为了让这些承诺成立，实现时要满足（写给以后的实现 PR，也作为评审清单）：

- 任何网页服务器都会在请求里看到访问者的 IP，所以文案用“不保存”而不是“不记录”。“不保存”只能由服务端配置做到，仓库里的测试证明不了：访问日志关闭或去掉 IP 字段，查完地区后立刻丢弃 IP，响应里只返回国家或地区代码。实现 PR 要附上可审查的服务端配置（去掉私有地址和密钥），供评审核对。
- 检查页静态、无第三方资源，响应加 `Cache-Control: no-store`。
- Mac 侧的出口查询同样只保留地区代码，不写日志，不写磁盘。现在的 Hachi 只观察网络路径是否可用，没有出口 IP 查询（README 写明“网络可用不等于验证过的出口 IP”），所以 Mac 侧查询是这个功能的前置依赖，要单独设计。
- 仓库里不放检查页服务器的私有地址、密钥或部署配置。
- 体验验收（G6，见 [AGENTS.md](../AGENTS.md) 和 [ux-checklist.md](ux-checklist.md)）：新增的菜单项、小圆点、菜单顶部提示、对照窗口的各个状态（第 3 节表格）、两边不同时的提醒，都要加进 `tests/ux_screens.py` 的截图，并在 `docs/ux-checklist.md` 里加对应的走查项。实现 PR 不能靠删减清单项通过。
- 发布前置条件：手机检查页和 Mac 窗口里“我们不保存 IP”的文案，要等服务端配置经维护者评审之后，才能进入任何发布版本（包括带后缀的预发布）。Mac 窗口的这句话同时覆盖 Mac 侧查询：只有 Mac 侧查询也走 Hachi 自己运维、配置经过评审的服务时才能写；如果 Mac 侧调用第三方地区服务，Mac 窗口只能写“Hachi 本身不保存 IP”，并写明第三方服务的名字。这条不放进 `release-gate.json`，由维护者在对应 issue 里记录。
- 文案硬约束：任何路径下，特别是手动填写路径下，都不得出现“相同，可以付款”“可以放心订阅”之类的暗示。“相同”时的提示只能是第 3 节第 6 步和第 5 节写定的两种说法，只在窗口里显示，不进菜单。实现 PR 按原文落地，改动要过评审。实现时建议在 `tests/branding.py` 或新测试里扫描界面字符串，禁用“可以付款”“放心订阅”“对齐”之类的措辞，把这条约定变成检查。
- 和 README 现有声明的关系：README 写着 Hachi 没有 telemetry、没有第三方依赖。Mac 侧出口查询和手机检查页都会向外部服务发请求，虽然只在用户主动点了之后才发、不上报使用数据，但已经超出 README 现在的描述。实现 PR 必须同时更新 README：说明有哪些外部请求、什么时候发、发给谁、只取什么，并说明这些不是 telemetry 的理由。如果用了第三方地区查询服务，就要在 README 里如实写成外部依赖，不能继续写“no third-party dependency”。现在的测试（包括 `tests/branding.py`）不检查这些声明，所以实现 PR 要考虑加一项检查，或者在 PR 范围检查里手动核对。

## 7. 待定问题

1. 检查页放在哪里、谁运维。这需要一个公开的 HTTPS 页面，是 Hachi 目前没有的服务端组件，需要维护者决定。
2. 国家或地区数据库用哪一个，多久更新。出口地区本身是根据 IP 推断的，会有误差；文案已经写“出口所在的国家或地区”，不说“你在哪里”。
3. 以后要不要让手机把地区代码通过一次性配对码传回 Mac 自动对照。好处是少一步，代价是要多一个服务端接口和一次性令牌。第一版不做。
4. 手机开着 iCloud 专用代理或运营商代理时，检查页看到的出口可能和应用商店看到的不同。第一版只在帮助文字里如实说明“检查页看到的出口可能和应用商店看到的不同”，不建议用户关闭这些功能或改网络，不单独处理。
5. 范围确认：预检弹窗里的入口（那个弹窗的标题是“预检通过/未通过”，和“两边相同”放在一起，容易被读成可以付款的信号）和网络变化提示，对用代理的用户可能被当成“确认两台设备出口一致”的工具。这两个触发时机是维护者 2026-11-25 要求的，文档已去掉付款定位和隧道检测，但是否保留、还是第一版只留菜单里的主动入口，需要维护者在 issue 里明确确认。
