# Hachi · 小八

![Hachi, a Shiba Inu wagging its tail](docs/assets/hachi-logo.gif)

Hachi (ハチ) is a little watchdog for macOS. The menu-bar dog continuously wags its tail while running and stays still with macOS Reduce Motion. The animation is decorative, not a network health indicator. [Read the market research and sources](docs/market-research.md).

Development prototype (the repository is public since 2026-11-26; the app is unsigned by Apple and not notarized). A native macOS menu-bar app; it observes macOS network-path availability and optionally invokes already-installed `claude-safe` / `codex-safe` preflight adapters on demand. It does **not** enforce runtime network policy or cover browser authorization or MCP. It has no login-item registration, telemetry, automatic credential use, runtime blocking or third-party dependency. Network availability is not proof of a verified egress IP.

## Build / test

Requirements: macOS, Apple command-line tools, and Python 3.9+. The app is a universal binary (Apple silicon `arm64` and Intel `x86_64`), compiled for a macOS 13.0 deployment target but only tested on macOS 15; the single release package is launched on an Apple silicon runner and on an Intel runner before it is published (`tests/verify_package.py`). v0.2-dev.2 and earlier were arm64-only.

```sh
python3 build.py
python3 tests/lab.py
python3 tests/branding.py
python3 tests/ux_screens.py   # renders every menu and alert state (light/dark)
python3 tests/acceptance.py   # all of the above + screenshot baseline, hygiene and gate report in build/acceptance/
open 'build/Hachi.app'
```

The pixel comparison of the screenshots with [`tests/ux-baseline/`](tests/ux-baseline/README.md) only counts on CI: off CI, `tests/ux_baseline.py` (and so `tests/acceptance.py`) runs its self-test and skips the comparison, because a local render never matches the CI baseline. Use `python3 tests/ux_baseline.py --compare-locally` to look at the differences anyway, and `--import-log <CI job log>` to take a new baseline from CI. The release workflow runs the same comparison. All commands, workflows and who does what are in [docs/orchestration.md](docs/orchestration.md).

The test harness starts a real HTTP observer on loopback. It never runs an official provider client, reads a provider credential or sends traffic off-device. `tests/check.py` is an optional manual preflight smoke test for machines with the two local adapters, not part of acceptance or CI. Neither test represents a provider risk or ban outcome.

## Release gate (not met)

- Require at least 95% successful end-to-end operations in each declared workflow (desktop, CLI, browser authorization, MCP where supported), on a preregistered held-out scenario matrix spanning supported OS/architectures. Record counts, environments, repeated seeds, timing and uncertainty. Do not pool easy scenarios to hide a failing workflow.
- Critical failures block release independent of the percentage: zero observed direct or wrong-route egress for protected flows in the failure matrix, and no interruption or route change for unrelated control workloads. Verify at an independent network observer; app logs alone do not count. Missing coverage is not a pass.
- Initial lab cases: TCP/TLS streams including reconnect and token-like refresh, system/browser redirect and loopback callback, DNS IPv4/IPv6/UDP, MCP stdio child isolation and remote streaming. Inject route change, tunnel/core loss, already-open flows, sleep/wake, interface switch, update and extension disable/restart. Use isolated machines and synthetic credentials, never the user's provider accounts.
- Transfer evidence: exercise the same final OS enforcement mechanism across fixture clients and real signed client binaries in isolated homes. First validate process/signature identity and helpers by credential-free runs; only include official supported test endpoints or dedicated explicitly authorized test credentials if independently available. Match transport, process ownership, redirects and DNS behavior, and document gaps. Fixtures cannot establish vendor authentication UX, compatibility of unobserved flows, account eligibility, or provider enforcement outcomes. Do not claim those are validated or release an unverified surface as covered.
- Key blocker: signed Network Extension feasibility and independent test of behavior when extensions are unavailable. No launch-time status or synthetic canary substitutes for a data-plane test.
- UX acceptance: CI renders every menu-bar, menu and alert state in light and dark appearance (`tests/ux_screens.py`, in the CI artifact under `acceptance/ux/`), and the maintainer walks through [`docs/ux-checklist.md`](docs/ux-checklist.md) on a real Mac at the released commit and signs off. The screenshots draw the real menu items rather than capturing the system menu bar, so the walkthrough is what covers the actual interaction.

Automated checking: the gate is kept in machine-readable form in [`release-gate.json`](release-gate.json) and evaluated by `tests/acceptance.py` on every CI run from evidence under [`evidence/`](evidence/README.md); missing evidence is not met, the 95% rate is judged on its Wilson lower bound (at least 73 all-successful runs per workflow), and CI checks format, thresholds and git history only, not that the runs really happened (details and limits in [`evidence/README.md`](evidence/README.md)). The `Acceptance backlog` workflow is designed to keep one `acceptance` issue per item (its issue sync is not covered by automated tests): open while unmet, marked when the format check passes so the maintainer can close it, and reopened if the item regresses. `release.yml` can be started three ways, all only by the maintainer account: merging a PR that adds `docs/release-notes/v<version>.md` (the file name becomes the tag, and the release body is that file plus the acceptance report), running it by hand with `version` empty (the next `-dev.N` is picked) or filled in, or pushing a `v*` tag; the tag is created only after the build passes, and a pre-release is published directly. The rest of this paragraph describes the gate and the draft path, which now applies to stable tags only: `release.yml` is written so that a stable tag (`v0.2`) at the head of `main` releases only when every item is met, and a suffixed tag (`v0.2-dev.1`) publishes a prerelease marked as not meeting the gate; both still require the baseline checks to pass. For a stable tag the publish job waits for approval only if the `release` environment has required reviewers; none are configured yet (the repository was private until 2026-11-26 and its plan offered none), so a stable tag currently produces a draft release (with the app attached) that the maintainer publishes by hand; publish that draft rather than creating a new release. A pre-release (suffixed tag) is published directly. If a release for the tag already exists, the workflow attaches the app and acceptance report to it instead, and running the Release workflow by hand with an existing tag rebuilds and re-attaches them. The draft path and the manual re-attach to a published release each ran once, with `v0.2-dev.1`; a tag push onto an existing release has not run yet. G6 is met only by the maintainer's own sign-off; agents can fix the problems it finds but cannot sign it. CI checks only that the G6 record is complete and well formed: it cannot tell that the linked screenshots are from the tested commit or that the signer is the maintainer, and `tests/ux_screens.py` shows that every state renders and keeps its scope wording, not that rows grey out in the real system menu or that dark mode is readable (UX-09 and UX-12 cover those by hand). The G2/G3 lab cases do not have runners yet: CI runs the existing loopback lab, not the gate's cases, so those items are judged only from committed evidence. "Met" here means the maintainer's evidence claim passed the format and history checks; it is not independent verification that the runs happened.

Scope: compliant network reliability only, not altering provider account eligibility or bypassing platform enforcement. No private IP/config, account tokens, device paths, or live test credentials belong in the repo.

Contributing: all changes go through pull requests, including the maintainer's own; merges are manual. See [AGENTS.md](AGENTS.md) for the merge gate and what runs automatically (CI and acceptance, Codex and Claude PR review, and Claude implementation for issues labeled `claude` or comments starting with `@claude`), and [docs/orchestration.md](docs/orchestration.md) for the end-to-end flow, the model routing rule (Opus for lead decisions and the hardest logic, Sonnet for implementation from clear specs, review fixes, PR review and the daily report, Haiku for coordination, Codex for second-opinion review) and the daily usage review. PRs that change the screenshot baseline list every changed screenshot and are merged only after the maintainer has looked at the diff images.
