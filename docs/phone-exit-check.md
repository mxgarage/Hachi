# 手机出口对照：扫码配对交互设计

状态：设计稿，未实现。维护者 2026-11-25 选定“扫码配对”方案。

## 1. 目的和边界

很多人在 Mac 上浏览，在手机上订阅或付款（App Store、Google Play、平台 App 内购）。两台设备的网络出口可能不在同一个国家或地区，用户自己往往不知道。这个功能只做一件事：**让用户同时看到“这台 Mac 现在从哪里出去”和“手机现在从哪里出去”，由用户自己对照。**

边界（与 [AGENTS.md](../AGENTS.md) 的范围条款一致）：

- 只提醒，不拦截，不改任何网络设置，不替用户切换出口。
- 不判断出口“对不对”、能不能让账号或付款通过。出口位置不等于服务资格，平台按真实所在地和账号信息判断（证据包 A1、O2）。
- 不对不一致的情况给出任何绕开地区限制或平台风控的建议。
- 只显示到国家或地区一级，不显示城市、运营商或 IP。

## 2. 什么时候出现

| 时机 | 行为 | 说明 |
|---|---|---|
| 用户主动 | 菜单新增一项“对照手机出口…”，随时可用 | 主入口，永远可用 |
| 订阅或付款前 | “检查 Claude 出口 / 检查 Codex 出口”的结果弹窗（现在是 `NSAlert`，可以用 `addButton` 加第二个按钮）里，加一个“付款前对照手机出口”按钮 | 那个检查调用的是已安装的 `claude-safe` / `codex-safe` 预检适配器，不是 Hachi 自己的出口地区查询，所以这个按钮只是一个快捷入口，打开的仍是第 3 节的窗口；Mac 侧出口查询（第 6 节）做好之前，这个按钮不出现。Hachi 是菜单栏应用，看不到浏览器里打开了什么页面，所以不做“自动识别付款页”，这个入口靠用户在付款前顺手点一下 |
| 网络变化 | 网络变化稳定 30 秒后，菜单栏图标旁出现一个小圆点，菜单顶部出现“网络变了，要对照手机出口吗？” | 不弹窗、不发系统通知、不自动出二维码。触发条件见下面的说明 |

“网络变化”怎么算：`NWPath` 不提供网络标识（同名 Wi‑Fi 之间切换也分不出来），所以不按“是不是同一个网络”判断，只看 `NWPathMonitor` 能拿到的两样东西：正在使用的接口类型（Wi‑Fi、有线、蜂窝、其他）有没有变化，以及路径上有没有出现或消失 `utun` 这类隧道接口。`NWPath.availableInterfaces` 对隧道接口只报 `.other` 类型，能不能可靠地看出隧道接口的有无，要在实现前先验证；做不到就只看接口类型变化。这个判断只用来决定要不要提示“出口可能变了”，不记录、不展示用户有没有在用 VPN 或代理。规则：

- 只有接口类型或隧道接口的有无变了才算一次变化；只是从“不可用”恢复为“可用”、接口没变（例如睡眠唤醒、短暂掉线）不算。
- 变化后要稳定 30 秒才提示，期间再变就重新计时。
- 不管怎么变，两次提示至少隔 10 分钟。用户点“这次不用”后，下一次变化前不再提示。

盲区：在同一个 Wi‑Fi 下切换 VPN 或代理的出口节点时，接口类型和隧道接口的有无都不变，这条规则不会提示。所以“网络变化提示”不能代表出口变了，出口变化只能靠用户主动对照或付款前对照。

这个时机的价值要在实现后看实际打扰程度再定，如果误报多，可以先只保留主动入口和付款前入口。

二维码只在用户点了上面某个入口之后才生成和显示。Hachi 不在后台定时让手机去查。

## 3. 主流程

1. 用户点“对照手机出口…”。
2. Mac 先查自己的出口地区（见第 6 节依赖），然后弹出窗口：左边是二维码，右边是“这台 Mac：<地区>”。
3. 用户用手机相机扫码，手机浏览器打开检查页。
4. 检查页只显示一行大字“这部手机：<地区>”，下面一行小字是隐私说明（文案见第 4 节，承诺见第 6 节），再下面是“回到 Mac 上对照”。
5. 用户回到 Mac，窗口里有三个按钮：**“两边显示相同”**、**“两边显示不同”**、**“扫不了”**。
6. 选“两边显示相同”：关闭窗口，菜单里记一行“上次对照：你确认两边显示的地区相同（<时间>）”，只存在内存里，退出即清空。这一行只记录用户看到了什么，不代表可以付款，也不代表应用商店或平台看到的是同一个地区（见第 7 节第 4 条）。
7. 选“两边显示不同”：进入第 4 节的提醒。因为手机不回传结果，扫码路径下 Mac 不知道手机具体是哪个地区，提醒里只写 Mac 这一侧的地区，不替用户填手机的地区。

第一版里手机**不把结果传回 Mac**，由用户自己看两边的地区并点按钮。这样二维码里不需要任何会话标识，Mac 和检查页之间也没有连接。以后如果要自动对照，另开 issue 讨论（第 7 节）。

二维码内容只是固定的检查页地址，不带设备、用户或会话参数。因为地址固定，旧截图扫出来也是同一个页面，而页面只显示访问者自己当前的出口，所以旧码无害，不设过期机制。

## 4. 文案

### Mac 窗口

- 标题：对照手机出口
- 说明：用手机相机扫这个码，手机会打开一个页面，显示手机现在的网络出口在哪个国家或地区。看完回来点下面的按钮。
- Mac 侧：这台 Mac：日本（JP）
- Mac 侧查询失败：这台 Mac：暂时查不到。这时“两边显示相同 / 两边显示不同”两个按钮置灰，只留“重试”和“关闭”，不在菜单里留任何对照记录。
- 按钮：两边显示相同 / 两边显示不同 / 扫不了
- 二维码下方小字：扫不了的话，在手机浏览器里输入 <检查页短地址>
- 底部小字：只看国家或地区。我们不保存 IP，也不把手机的结果传回这台 Mac。

### 手机检查页

- 主文字：这部手机：日本（JP）
- 查询失败：暂时查不到这部手机的出口。可以关掉 Wi‑Fi 或切换网络后刷新一次。
- 隐私说明：这个页面只读取你的网络出口所在的国家或地区。我们不保存 IP，不用 Cookie，不收集其他信息。只有你扫码打开时才会查询。
- 底部：回到 Mac 上对照

### 两边不同时的提醒（Mac）

- 标题：你看到两台设备的网络出口不在同一个地区
- 正文：
  > 这台 Mac：日本（JP）
  > 这部手机：和上面不同（以手机页面显示为准）
  >
  > 这只是提醒。Hachi 不判断哪一个“对”，也不会帮你修改网络。
  >
  > 如果你接下来要订阅或付款，可以先确认：
  > · 账号和付款信息里填的，是不是你真实的所在地。
  >
  > 拿不准的话，请直接联系应用商店或对应服务的客服确认。
- 按钮：知道了

提醒里不出现“切换节点”“换成某地出口”“关掉/打开 VPN 再付款”之类的建议，也不出现“这样更安全”“不会被封”之类的承诺。

## 5. 手动兜底

扫不了码（没有相机权限、相机打不开链接）时，用户点“扫不了”：

- 第一步：显示检查页的短地址，说明“在手机浏览器里输入这个地址，结果和扫码一样”。看完后回到第 3 节第 5 步的两个按钮。这一步仍然只用 Hachi 自己的检查页，不引导用户去第三方 IP 查询网站。
- 第二步（手机不在身边，或检查页打不开）：说明“如果你已经知道手机现在的网络出口在哪个国家或地区，可以在这里选。这是你自己填的，Hachi 没法核实。”控件是国家或地区下拉列表（ISO 3166 列表，默认空），以及“我不知道”。
  - 这里只接受网络出口地区。应用商店账号的地区是另一回事（出口在美国的手机，商店账号可以设成日本），不能拿来代替，说明里写明“不要填应用商店账号的地区”。
  - 选了地区：和 Mac 侧比较。相同时菜单记“上次对照：你填的手机地区和这台 Mac 相同（未核实）”；不同时显示第 4 节的提醒，标题改为“你填的手机地区和这台 Mac 的出口不在同一个地区”，手机一行写“你填的：<地区>（未核实）”。
  - 选“我不知道”：只显示一句“没关系。付款前如果拿不准，请联系应用商店或对应服务的客服确认。”，然后关闭。

手动填的地区同样只存在内存里，不写磁盘。

## 6. 隐私说明和实现约束

对用户的承诺（同时写在手机检查页上）：

- 检查页只读取出口所在的国家或地区。
- 不保存 IP，不用 Cookie、本地存储或第三方统计脚本，不收集设备型号、浏览器指纹或位置权限。
- 只有用户扫码打开页面时才查询，Hachi 不会在后台让手机发请求。

为了让这些承诺成立，实现时要满足（写给以后的实现 PR，也作为评审清单）：

- 任何网页服务器都会在请求里看到访问者的 IP，所以文案用“不保存”而不是“不记录”。“不保存”只能由服务端配置做到，仓库里的测试证明不了：访问日志关闭或去掉 IP 字段，查完地区后立刻丢弃 IP，响应里只返回国家或地区代码。实现 PR 要附上可审查的服务端配置（去掉私有地址和密钥），供评审核对。
- 检查页静态、无第三方资源，响应加 `Cache-Control: no-store`。
- Mac 侧的出口查询同样只保留地区代码，不写日志，不写磁盘。现在的 Hachi 只观察网络路径是否可用，没有出口 IP 查询（README 写明“网络可用不等于验证过的出口 IP”），所以 Mac 侧查询是这个功能的前置依赖，要单独设计。
- 仓库里不放检查页服务器的私有地址、密钥或部署配置。
- 发布前置条件：手机检查页和 Mac 窗口里“我们不保存 IP”的文案，要等服务端配置经维护者评审之后，才能进入任何发布版本（包括带后缀的预发布）。这条不放进 `release-gate.json`，由维护者在对应 issue 里记录。
- 文案硬约束：任何路径下，特别是手动填写路径下，都不得出现“相同，可以付款”“可以放心订阅”之类的暗示。菜单记录只能是第 3 节第 6 步和第 5 节写定的两种说法，实现 PR 按原文落地，改动要过评审。
- 和 README 现有声明的关系：README 写着 Hachi 没有 telemetry、没有第三方依赖。Mac 侧出口查询和手机检查页都会向外部服务发请求，虽然只在用户主动点了之后才发、不上报使用数据，但已经超出 README 现在的描述。实现 PR 必须同时更新 README：说明有哪些外部请求、什么时候发、发给谁、只取什么，并说明这些不是 telemetry 的理由。如果用了第三方地区查询服务，就要在 README 里如实写成外部依赖，不能继续写“no third-party dependency”。现在的测试（包括 `tests/branding.py`）不检查这些声明，所以实现 PR 要考虑加一项检查，或者在 PR 范围检查里手动核对。

## 7. 待定问题

1. 检查页放在哪里、谁运维。这需要一个公开的 HTTPS 页面，是 Hachi 目前没有的服务端组件，需要维护者决定。
2. 国家或地区数据库用哪一个，多久更新。出口地区本身是根据 IP 推断的，会有误差；文案已经写“出口所在的国家或地区”，不说“你在哪里”。
3. 以后要不要让手机把地区代码通过一次性配对码传回 Mac 自动对照。好处是少一步，代价是要多一个服务端接口和一次性令牌。第一版不做。
4. 手机开着 iCloud 专用代理或运营商代理时，检查页看到的出口可能和应用商店看到的不同。第一版在“查询失败”和帮助文字里提一句，不单独处理。
