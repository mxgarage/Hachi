# Release-gate evidence

One JSON file per item in [`release-gate.json`](../release-gate.json), named by its `evidence` field. `python3 tests/acceptance.py` evaluates them; a missing or malformed file counts as not met.

Rules (see [AGENTS.md](../AGENTS.md)):
- Evidence comes from real lab runs measured at an independent network observer. App logs alone do not count.
- Only the maintainer commits files here. Agents build the harnesses that produce evidence; they never hand-write or edit these files.
- No private IPs, account tokens, device paths or live credentials. Use documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) where an address is needed, and link raw logs instead of pasting them.

Rules the evaluator applies: G1 is judged on the Wilson 95% lower bound (not the point estimate), so each workflow needs at least 73 all-successful runs; declared workflows cannot be waived except MCP ("where supported"), whose G3 lab cases may then be `not_supported`; only `none` or `synthetic` credentials are accepted.

What CI can and cannot check: `tests/acceptance.py` checks format, thresholds, and consistency with git history (`tested_commit` exists and is an ancestor of what is evaluated or released, product files unchanged since, the scenario matrix already existed at `tested_commit` and has not changed since (this does not prove it was registered before the runs, or that it is held out), raw records are pinned by SHA-256 and the hash of a file in `evidence/` is verified). It does not check that the matrix is held out, that the G1 `by_scenario` keys cover the scenarios in the matrix (the matrix file is not parsed), that environments span the supported OS/architectures, or that raw records match the reported counts; for G3–G5 it is essentially a format check. It cannot prove that a run happened or that the observer was independent. Those are the maintainer's claims, made by committing the file. A PR from a `claude/`, `codex/` or `muse/` branch, or with Claude/Codex co-author or session trailers, that touches `evidence/` fails CI; other agents or branch names are not detected. Changes to the gate definition (`release-gate.json`, `tests/acceptance.py`, `tests/gate_selftest.py`, `.github/workflows/`, `.github/scripts/`, `AGENTS.md`, this file) only produce a warning: keeping agents from loosening the gate relies on the maintainer's review, not on CI. G2 requires zero critical failures in every G3 scenario (normal cases and `inject_*` fault injection; MCP cases are skipped only when met G1 evidence marks MCP unsupported) with a minimum number of observed flows, but whether those flows were really observed is again the maintainer's claim.

Test on a commit that is already on `main`. PRs here are merged with merge commits; a squash or rebase merge drops the branch commits from `main`'s history, and evidence recorded against them can never pass.

Coupling to note: any change to a product file (every tracked file except `docs/`, `evidence/`, `tests/acceptance.py`, `tests/gate_selftest.py`, `.github/`, Markdown, `release-gate.json` and `.gitignore`; evidence runners under `tests/` do count) makes all evidence stale. Once the README heading says `(met)`, such a PR fails the baseline until the heading goes back to `(not met)` in the same PR, or new evidence for that commit is committed.

Fields every file needs: `tested_commit` (40-character SHA), `environments` (OS/architecture list), `credentials` (`none` or `synthetic`; no authorized or live credentials), `raw_results` (`{"path": "evidence/…", "sha256": "…"}` or `{"url": "https://…", "sha256": "…"}`). For `path`, CI verifies the hash and rejects the gate evidence files themselves, but (unlike the matrix) does not check that the raw file, `gaps_document` or `feasibility_document` already existed at `tested_commit`; for `url`, CI does not download the file, so its hash is only the maintainer's record. G1 slices (`by_scenario`, `by_environment`) need at least `min_slice_attempts` runs each and are judged on their point estimate, not the Wilson bound, which would need about 73 runs per slice; only the workflow total uses the lower bound. G6 (`G6-ux-signoff.json`) is the maintainer's walkthrough of `docs/ux-checklist.md`: `checks` maps every `UX-nn` ID in the checklist to `{"result": "pass", "note": …}`, `appearances` lists at least `light` and `dark`, `screenshots_run` links the CI run of `tested_commit` whose `acceptance/ux/` screenshots were compared, and `signed_off_by` / `signed_off_at` (YYYY-MM-DD) record the sign-off. The checklist must already exist at `tested_commit` and be unchanged since; CI checks that the run belongs to this repository, but not that it is for that commit. The per-item fields are checked in `tests/acceptance.py`; `tests/gate_selftest.py` shows a complete example for each item.
